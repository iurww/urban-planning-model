# 数据格式

本文描述当前 OSM → abstract → expert → training 管线生成的文件。每套数据使用独立的
`<dataset-root>`；正式数据可以取 `data/`，验证数据可以取 `datadoc/`。规范样例路径为：

```text
<dataset-root>/<candidate-dir>/tianjin_4km_c128_r1083/
  evidence/
  abstract/
```

训练链接 `<dataset-root>/train/tianjin_4km_c128_r1083` 指向上述 `abstract/`。
`prepare-training-data` 不复制或改写候选文件，只生成选择表、划分报告和符号链接。

## 1. 全局约定

### 1.1 坐标和单位

- `abstract/topology.json` 几何使用 tile 局部米制坐标；原点是
  `metadata.local_origin_in_source_crs`。
- `metadata.source_crs` 是 UTM 等投影 CRS；`tile_size_m=4000`。
- `evidence/*.geojson` 几何通常是 WGS84；米制派生值明确以 `_m`、`_m2` 结尾。
- SUMO plain XML 和 net 使用同一局部米制坐标。

### 1.2 ID

| 实体 | 格式 | 说明 |
|---|---|---|
| 地块 | `parcel/p0000` | `parcels[]` 中稳定字符串 ID |
| 道路 | `road/r0000` | `roads[]` 中稳定字符串 ID |
| 支撑点 | `intersection/i0000` | junction 或 boundary portal |
| SUMO node | `node_intersection_i0000` | 由支撑点 ID 派生 |
| SUMO directed edge | `edge_road_r0000_fwd/rev` | 由道路 ID 和方向派生 |

三个 solution CSV 另用从 0 开始的行下标：`parcel_id` 等于 `parcels[]` 下标，
`road_row_index` 等于 `roads[]` 下标；如有 `source_id`，它必须与上述字符串 ID 一致。

## 2. 数据集根文件

### 2.1 `<dataset-root>/topology_selection.csv`

| 列 | 含义 |
|---|---|
| `tile_id` | `topology.json.metadata.tile_id` |
| `city` | 城市名 |
| `topology_path` | 相对 selection CSV 的 canonical topology 路径 |
| `split` | `train` 或 `test` |

prepare 对该文件采用只追加语义：保留已有行和 split，只追加本轮自动选择的新 tile。

### 2.2 `<dataset-root>/topology_selection.split_report.json`

| 字段 | 含义 |
|---|---|
| `schema_version` | 当前为 1 |
| `generator` | `scripts.prepare_training_data` |
| `data_root`, `candidate_count` | 候选根目录和扫描到的候选总数 |
| `complexity_bounds` | 尺寸、P/R/I/J、结构复杂度阈值 |
| `complexity_eligible_count` | 通过复杂度和交通契约的数量 |
| `complexity_rejection_counts` | 各过滤原因的数量 |
| `complexity_rejected[]` | 被过滤 tile、原因和 P/R/I/J 统计 |
| `land_feasible_candidates` | 通过 Land 面积配额整数可行性检查的数量 |
| `land_infeasible_rejected[]` | Land 配额不可行的 tile 与求解器信息 |
| `train_count`, `test_count` | 本轮自动选择请求数量 |
| `selection_update` | 已有、自动生成、新增、最终行数和最终 split 计数 |
| `feature_balance`, `matched_groups` | train/test 形态匹配统计 |

### 2.3 `<dataset-root>/{train,test}/selection_manifest.json`

顶层：`schema_version`、`split`、`count`、`created`、`updated`、`unchanged`、
`removed`、`data_root`、`link_output_root`、`selection_csv`、`tiles[]`。

`tiles[]` 每行包含 `tile_id`、`split`、canonical `source` 和符号链接 `link`。

### 2.4 失败 TSV

`static_solve_failures.tsv` 是制表符文件，记录失败 tile 和异常信息；成功批次会清空
对应 fail log。它是诊断文件，不进入训练。

## 3. `evidence/`：OSM 清洗证据

该目录用于审计，不由 `load_urban_graph()` 读取。

### 3.1 GeoJSON 公共结构

`parcels.geojson`、`roads.geojson`、`intersections.geojson`、`signals.geojson`、
`audit_rejected_signals.geojson`、`landuse_source.geojson` 均为：

```json
{
  "type": "FeatureCollection",
  "metadata": {},
  "features": [
    {"type": "Feature", "id": "...", "properties": {}, "geometry": {}}
  ]
}
```

### 3.2 `parcels.geojson`

每个 Feature 是证据阶段规划面。properties：

| 字段 | 含义 |
|---|---|
| `id` | 证据地块 ID |
| `area_m2`, `perimeter_m` | 面积、周长 |
| `bbox_width_m`, `bbox_height_m` | 米制包围盒尺寸 |
| `centroid_x_m`, `centroid_y_m` | 源投影下质心 |
| `compactness` | 紧致度 |
| `land_use` | 映射后的 OSM 土地标签 |
| `landuse_coverage_ratio` | 来源 landuse 覆盖比例 |
| `source_landuse_ids[]` | 来源面 ID |
| `source` | 生成来源 |
| `touches_tile_boundary` | 是否接触 tile 边界 |

### 3.3 `roads.geojson`

| 字段 | 含义 |
|---|---|
| `id`, `from_intersection`, `to_intersection` | 逻辑路和两端证据路口 |
| `highway`, `highway_members`, `name`, `ref` | OSM 道路分类/名称 |
| `is_link` | 是否匝道/link |
| `member_edge_count`, `member_osm_way_ids[]` | 聚合来源 |
| `carriageway_count`, `carriageway_length_m` | 合并车行道统计 |
| `logical_length_m` | 逻辑道路长度 |
| `total_lanes`, `turn_lanes`, `oneway_members` | 交通属性 |
| `speed_kph`, `width_m` | 限速与宽度 |
| `lane_data_inferred`, `speed_inferred`, `width_inferred` | 是否推断 |
| `boundary_endpoint_count`, `source` | 边界端点数与来源 |

### 3.4 `intersections.geojson`

properties：`id`、`member_count`、`member_osm_node_ids[]`、
`branch_osm_node_ids[]`、`incident_osm_way_count`、`logical_road_degree`、
`raw_degree_max`、`cluster_diameter_m`、`grade_layers[]`、`signalized`、
`signal_head_count`。

### 3.5 `signals.geojson` 与 `audit_rejected_signals.geojson`

properties：`id`、`osm_node_id`、`kind`、`tags`、`on_road_graph`、
`attached_intersection`、`attachment_distance_m`。前者是保留信号头，后者记录因离路网
过远等原因拒绝的信号头。

### 3.6 `landuse_source.geojson`

properties：`id`、`osm_area_id`、`land_use`、`area_m2`、`tags`；保存抽象地块标签的
OSM 来源面。

### 3.7 `edges.jsonl`

每行一条图关系：

| 字段 | 含义 |
|---|---|
| `id` | 关系稳定 ID |
| `relation` | `road_intersection`、`road_road`、`parcel_road` 等 |
| `source`, `target` | 两端实体 ID |
| `directed` | 是否有向 |
| `properties` | 关系特定属性，如 `endpoint` |

### 3.8 `topology.json`（证据图）

| 字段 | 含义 |
|---|---|
| `pipeline_version`, `generated_at` | 生成版本和时间 |
| `input` | PBF 路径 |
| `metric_crs` | 计算 CRS |
| `tile` | `tile_id/city/crs/column/row/size_m/bounds_m/bbox_wgs84/polygon_wgs84/stats` |
| `nodes[]` | `id/node_type/x_m/y_m/properties` |
| `edges[]` | 与 JSONL 相同的关系对象 |
| `geometry_layers[]` | 各 GeoJSON 文件的名称/语义 |
| `traffic_control_file` | `traffic_control.json` 引用 |

### 3.9 `schema.json`

定义证据数据的 `schema_version`、`node_types`、`edge_types`、
`coordinate_systems`、`dynamic_data_boundary` 与 `id_stability`。它是可读模式说明，不是
JSON Schema 校验器文件。

### 3.10 `quality_report.json`

| 字段 | 含义 |
|---|---|
| `counts` | 原始和抽象要素数、各 edge type 数 |
| `metrics` | 合并率、推断率、图分量、重叠面积等 |
| `invariants` | 每条质量规则的 `passed` 与 `evidence` |
| `extractor_stats` | PBF 提取统计 |
| `junction_clustering`, `path_collapse`, `parcel_generation`, `signal_processing` | 各阶段统计 |
| `refinements_from_v3` | 相比旧版的处理记录 |
| `warnings` | 非致命警告 |
| `dynamic_data_note` | 动态值来自 SUMO 的说明 |

### 3.11 `traffic_control.json`

顶层 `input/metric_crs/tile/pipeline_version/generated_at` 是来源；`phase_actions[]`
定义 8 个 canonical movement；`controls[]` 包含
`intersection_id/signal_head_ids/signal_head_count/approach_slots/movements/`
`available_phase_mask/neighbor_intersection_ids/static_features`；
`observation_schema` 与 `reward_schema` 描述运行时接口。

### 3.12 `sumo_static_seed.json`

是 evidence 图到 SUMO 的早期静态映射：`schema_version`、`coordinate_system`、
`geometry_file`、`tile`、`note`、`phase_actions[]`、`roads[]`、`controllers[]`。
`roads[]` 保存端点、车道、限速和推断标记；`controllers[]` 保存 phase mask、approach、
movement 和信号头证据。正式仿真以 `abstract/traffic_signals.json` 为准。

### 3.13 PNG

`overview.png` 是证据图总览；`signal_topology.png` 是信号附着与控制关系图。两者只用于
人工质检。

## 4. `abstract/topology.json`

顶层：

| 字段 | 类型 | 含义 |
|---|---|---|
| `schema_version` | string | `abstract-urban-topology-*` |
| `metadata` | object | tile/重建/质量元数据 |
| `parcels` | array | 规划面 |
| `roads` | array | 双向抽象道路 |
| `intersections` | array | junction 与 boundary portal |

### 4.1 `metadata`

基础字段：`tile_id`、`coordinate_system=local_metric`、`unit=meter`、
`local_origin_in_source_crs[x,y]`、`source_crs`、`tile_size_m`、`tile_width_m`、
`tile_height_m`、`tile_area_m2`、`is_exact_square`。

统计/审计对象：

| 对象 | 内容 |
|---|---|
| `construction` | 道路、交叉口、地块抽象原则和 hierarchy |
| `source_stats` | 输入道路/节点、选取类别和排除原因 |
| `parallel_corridor_processing` | 平行走廊压缩统计与例子 |
| `reconstruction_stats` | noding、剪枝、折点折叠统计 |
| `face_regularization` | 删除边以修复坏地块的逐次审计 |
| `parcel_stats` | 面覆盖、形状质量统计 |
| `validation` | 引用完整性、几何、覆盖、交叉等检查 |
| `synthetic_lane_defaults` | 2/3 车道归一化统计 |
| `signal_control_defaults` | all-junction signal 与 8-action 策略 |
| `road_geometry_normalization` | polyline 合并统计 |
| `dataset_provenance` | 筛选复制模式添加的 city/source/score/信号统计 |

### 4.2 `parcels[]`

| 字段 | 含义 |
|---|---|
| `id` | 字符串主键 |
| `geometry` | Polygon rings：`[[[x,y],...], hole1,...]` |
| `land_use` | OSM 来源类别，不是专家规划标签 |
| `source_landuse_ids[]` | 来源 evidence ID |
| `area_m2`, `perimeter_m` | 面积和周长 |
| `min_rotated_width_m`, `rotated_aspect_ratio` | 旋转包围盒形状 |
| `compactness`, `convexity_ratio`, `rectangularity_ratio` | 形状指标 |
| `hole_count` | 内环数 |
| `boundary_vertex_count`, `noded_boundary_vertex_count`, `corner_count` | 顶点/角点数 |
| `min_interior_angle_deg`, `max_interior_angle_deg` | 内角范围 |
| `quadrilateral_parallel_error_deg` | 四边形平行误差 |
| `boundary_road_ids[]` | 边界道路 |
| `corner_intersection_ids[]` | 角点支撑点 |
| `neighbor_parcel_ids[]` | 邻接地块 |

### 4.3 `roads[]`

| 字段 | 含义 |
|---|---|
| `id`, `from_intersection_id`, `to_intersection_id` | 主键与端点 |
| `geometry` | `[[x,y],...]`，允许合法 polyline |
| `length_m` | polyline 长度 |
| `name`, `highway` | 来源道路属性 |
| `total_lanes`, `lanes_per_direction` | 当前语义均为每方向抽象车道数 |
| `lane_count_semantics`, `lane_index_order` | 车道数和编号契约；0 为最右 |
| `speed_kph` | 限速 |
| `lane_data_inferred`, `speed_inferred` | 是否推断 |
| `source_total_lanes`, `source_lane_data_inferred` | 归一化前值 |
| `source_carriageway_count` | 合并车行道数 |
| `source_road_ids[]`, `source_osm_way_ids[]`, `source_corridor_ids[]` | 来源追踪 |
| `source_segment_ids[]`, `source_segment_count` | polyline 合并来源段 |
| `geometry_regenerated` | 是否重建几何 |
| `intersection_ids[]` | 两端支撑点（兼容字段） |
| `adjacent_road_ids[]`, `parcel_ids[]` | 图邻接 |
| `lane_connections[]` | `lane_index/lateral_position/allowed_turn_types/speed_kph` |
| `lane_assignment_policy` | 当前 `abstract-road-default-v1` |

### 4.4 `intersections[]`

| 字段 | 含义 |
|---|---|
| `id`, `point[x,y]` | 主键和局部坐标 |
| `kind` | `junction` 或 `boundary_portal` |
| `degree` | 道路度 |
| `road_ids[]` | incident 道路 |
| `neighbor_intersection_ids[]` | 一跳支撑点 |
| `parcel_ids[]` | 相邻地块 |

只有 `kind=junction` 进入模型实体；portal 仍被 Road reward 和 SUMO 使用。

## 5. `abstract/traffic_signals.json`

这是清洗阶段冻结的 SUMO 静态合同，schema 当前为
`abstract-traffic-signals-2.0`。

### 5.1 顶层

| 字段 | 含义 |
|---|---|
| `schema_version`, `readiness_level` | 模式和可运行级别 |
| `metadata` | tile、拓扑文件/hash、右行交通、推断策略 |
| `signalized_intersection_ids[]` | 当前所有真实 junction ID |
| `phase_actions[]` | canonical `action_id/name/movement_keys` |
| `controllers[]` | 每路口控制器 |
| `detectors[]` | 静态 detector 定义 |
| `sumo_network` | 可直接序列化的 nodes/edges/lanes/connections |
| `mapping_report` | OSM signal 到抽象 junction 的映射统计 |
| `observation_schema`, `reward_schema`, `rl_control_schema` | RL 接口说明 |
| `od_demand_contract`, `simulation_contract` | OD 与仿真约束 |
| `validation` | errors/warnings/checks/passed |

### 5.2 `controllers[]`

身份/映射：`id`、`intersection_id`、`sumo_tl_id`、`controller_source`、
`source_intersection_ids[]`、`source_signal_head_ids[]`、`source_signal_head_count`、
`maximum_source_mapping_distance_m`。

结构：`approach_slots`、`movements`、`controlled_links`、`observation_lane_ids[]`、
`pressure_outgoing_lane_ids[]`、`detector_ids[]`、`neighbor_controller_ids[]`、
`neighbor_controllers`、`static_features`、`signal_group_generation`。

动作：`available_phase_mask[8]` 与 `program`。`program` 内含 `actions[]`、
`available_action_mask`、`initial_action_id`、`all_red_state`、`state_length`、
`state_character_order`、`state_alphabet`、`control_mode`、`sumo_program_id`、
`bootstrap_tl_logic`。每个 action：`action_id/name/available/green_state/yellow_state/`
`movement_keys/protected_link_indices/permissive_right_link_indices/`
`minimum_green_s/maximum_green_s`。

### 5.3 `sumo_network`

顶层：`schema_version`、`coordinate_system`、`lane_index_convention`、
`nodes[]`、`directed_edges[]`、`lanes[]`、`connections[]`、
`boundary_entry_edge_ids[]`、`boundary_exit_edge_ids[]`、`plain_xml_files`、
`netconvert`。

- node：`id/topology_intersection_id/x_m/y_m/type/fringe/tl_id`。
- directed edge：`id/topology_road_id/direction/from_* /to_* /shape/length_m/`
  `num_lanes/lane_ids/road_class/name/priority/speed_limit_kph/speed_limit_mps/`
  `allow_vehicle_classes` 与推断标记。
- lane：`id/edge_id/index/index_order/topology_road_id/direction/from_intersection_id/`
  `to_intersection_id/length_m/width_m/speed_limit_*/function/lateral_position/`
  `allowed_turn_types/default_allowed_turn_types/allowed_connection_ids/`
  `controlled_movement_ids/allow_vehicle_classes` 与推断标记。
- connection：`id/from_edge_id/to_edge_id/from_lane_id/to_lane_id/from_lane_index/`
  `to_lane_index/via_intersection_id/origin_slot/destination_slot/turn_type/u_turn/`
  `controller_id/sumo_tl_id/link_index/movement_key`。

## 6. 三类静态专家文件

### 6.1 solution CSV

`land_use_solution.csv`：

| 列 | 含义 |
|---|---|
| `parcel_id` | 0-based 地块下标 |
| `source_id` | 可选字符串地块 ID |
| `area` | m² |
| `land_use` | `grn/com/res/sch/hos/off` |

标签含义：`grn` 绿地、`com` 商业、`res` 住宅、`sch` 学校、`hos` 医疗、`off` 办公。

`road_plan_solution.csv`：`road_row_index`、`upgraded`（0/1）、可选 `source_id`。

`poi_plan_solution.csv`：`parcel_id`、`place_poi`（0/1）、可选 `source_id`。

### 6.2 trajectory JSON 公共字段

| 字段 | 含义 |
|---|---|
| `task_type` | `land_use_planning` / `road_planning` / `poi_placement` |
| `objective` | 数学目标文字 |
| `constraints` | Road 可选，骨架约束说明 |
| `reward_timing` | `terminal_only` |
| `metrics` | 终局指标与 `solver_objective` |
| `num_steps` | 原始完整二进制/分类决策数 |
| `num_poi` | POI 独有 K |
| `final_reward` | 与 solver objective 校验一致的标量 |
| `steps[]` | 逐步记录 |

每个 step：`t`（1-based）、`state`、`action`、`reward`、`return_to_go`。除最后一步外
`reward=0`；因为静态 gamma=1，每步 RTG 都等于 `final_reward`。

任务特定 state/action：

| 任务 | `state` | `action` |
|---|---|---|
| Land | `parcel_id/assigned_count/remaining_count` | `parcel_id/land_use` |
| Road | `decided_roads_count/upgraded_roads_count` | `road_row_index/upgraded` |
| POI | `placed_count/remaining_parcels/remaining_slots` | `parcel_id/place_poi` |

Land metrics：`Service`、`Ecology`、`alpha_Service`、`r_L`、
`residential_area/count`、`solver_objective`。

Road metrics：`Tdensity/Tconnectivity/Tspacing/Traffic` 及分项，`NCC/dead_ends/`
`too_long/too_short/length_sum_m/selected_roads/budget/budget_utilization`，
solver `mip_gap/runtime/status/objective`，以及 junction/portal 覆盖、原图分量、绕行和
非树骨架检查。

POI metrics：`r_POI`、`solver_objective`。

注意：SFT 的 Land 会按实际 training split 中 land label 的总频数从低到高重排 block。
Road expert plan 把 `upgraded=1` 视为默认保留的稠密骨架，只把较小的
`upgraded=0` 补集展开为“给定 delete=0，指向哪条道路”的监督步；默认对删除顺序做
8 次 permutation，每一步还保存剩余专家删除集合的 `target_mask`（内存字段，不回写
JSON）。原始轨迹仍保留全部道路/地块二进制动作。POI 轨迹当前不被训练加载。

## 7. `sumo/` 文件

| 文件 | 格式与作用 |
|---|---|
| `network.nod.xml` | `<node id x y type tl?>` plain nodes |
| `network.edg.xml` | `<edge id from to numLanes speed priority shape allow?>` |
| `network.con.xml` | `<connection from to fromLane toLane tl? linkIndex?>` |
| `network.tll.xml` | 顺序无关的 bootstrap：先全红，再逐 link slot 单独绿灯和黄灯 |
| `net.xml` | `netconvert` 编译网络；内部 edge 也在此 |
| `routes.xml` | `<vType>` + 精确 N 个 `<vehicle depart><route edges>` |
| `demand_manifest.json` | OD 参数与规划道路覆盖证明 |

`demand_manifest.json` 的主要字段为：

- 基本参数：`schema_version/seed/vehicle_count/depart_begin_s/depart_end_s/route_generation`；
- OD 配额：`boundary_od_target_fraction/boundary_od_vehicle_count/`
  `boundary_od_actual_fraction/arbitrary_od_vehicle_count/arbitrary_od_actual_fraction`；
- 覆盖与合法性：`required_topology_road_count/planned_covered_topology_road_count/`
  `planned_road_coverage/planned_directed_edge_count/route_validity/`
  `sumo_route_validation_passed`；
- 路线长度：`route_length_edges/two_edge_route_count/two_edge_route_fraction/`
  `three_or_more_edge_route_count/three_or_more_edge_route_fraction/short_route_exception`；
- 出发速度：`depart_speed_strategy/depart_speed_mps/depart_speed_factor`。

`depart_speed_strategy` 记录 seed 控制的速度比例分布及安全停车上限。生成器按起始边
长度、车辆长度、最小间距和减速度限制 `departSpeed`，避免车辆从受红灯控制的较短
起始边出发时因无法在路口前停车而被 SUMO 拒绝插入。

`short_route_exception` 仅记录 passenger lane-connection 图中经穷举证明无法构成三边
简单路线、但为覆盖对应抽象道路或满足 boundary OD 配额所必需的短路线。另保留
`legacy_horizon_argument/legacy_period_argument` 兼容字段。

## 8. `signal_meta.json`

这是一次专家采集冻结出的运行合同：

| 字段 | 含义 |
|---|---|
| `schema_version`, `task_type` | 模式和 `signal_control` |
| `topology_ref`, `signals_ref`, `net_file`, `route_file` | 同 tile 相对引用 |
| `phase_representation` | `canonical_action_id_0_to_7` |
| `transition` | 动作改变：3 s yellow + 12 s green；动作不变：保持原灯态 15 s |
| `control` | `delta_t/yellow_s/green_s/step_length/horizon/warmup/num_steps/time_to_teleport_s` |
| `termination` | 固定时域截断；不要求全部出发、全部到达或实际道路全覆盖 |
| `demand` | 完整复制 demand manifest |
| `reward` | `type/normalization/terminal_wait_weight` |
| `junctions[]` | 控制器运行子集 |

`junctions[]`：`junction_id/source_id/controller_id/tls_id`、`incoming_lanes[]`、
`observation_lane_ids[]`、`controlled_links[]`、`available_phase_mask[8]`、
`green_phases[]`、`phase_states[]`、`yellow_states[]`、`all_red_state`、
`initial_action_id`、`actions[]`。action 字段与第 5.2 节一致；controlled link 包含
connection/edge/lane/link index、turn type 和 movement key。这里的
`controlled_links[]` 与所有灯态字符串已经从 `traffic_signals.json` 的契约顺序转换为
compiled `net.xml` 的实际 `linkIndex` 顺序；回放和 PPO 启动时会再次用 TraCI 的
from/to lane 身份逐 index 校验。

## 9. `signal_trajectory.json`

顶层：

| 字段 | 含义 |
|---|---|
| `task_type` | `signal_control` |
| `topology_ref`, `meta_ref` | 同 tile 引用 |
| `expert` | `max_pressure_canonical_8_action` |
| `objective` | MaxPressure over legal canonical actions |
| `num_signalized`, `num_steps` | J 和固定 80 |
| `final_reward` | 当前为 0；奖励全部在 step 中 |
| `metrics` | 完整 episode 统计 |
| `steps[]` | 80 个联合决策 |

metrics：`arrived/departed/expected_vehicles`、`unfinished_vehicles`、
`pending_departure_at_horizon/running_at_horizon/sumo_min_expected_at_horizon/`
`final_sim_time_s`、
`mean_total_halt/total_wait_accumulated`、`teleport_started/ended`、
`required_topology_roads/route_covered_topology_roads`、
`actually_visited_topology_roads/road_coverage`、`remaining_by_edge`。
采集时 SUMO 的 `--time-to-teleport` 固定为 600 秒；`teleport_started/ended` 是实际
触发计数，`arrived` 包含的车辆不能单独证明没有 teleport。轨迹在固定 1200 秒结束，
未出发、运行中或未到达车辆以及实际未访问道路只作为终止指标，不导致采集失败；规划
OD 的合法性和道路覆盖仍由 `demand_manifest.json` 严格保证。

每步：

| 字段 | 含义 |
|---|---|
| `t`, `sim_time` | 1-based 决策序号和开始仿真秒 |
| `global_state.running` | 当前运行车辆 |
| `global_state.arrived_cum/departed_cum` | 累计车辆 |
| `global_state.total_halt` | 全网停车车辆 |
| `junctions[]` | J 个状态/动作 |
| `reward` | `-total_halt / J` |

每个 junction：`junction_id/source_id`，`state.cur_phase/phase_elapsed/`
`phase_pressure[8]/queue/wait/veh`，`action.action_id/green_idx`。

## 11. 训练产物格式

### 11.1 `data_split.json`

每次 `up-model-train` 在模型创建前写出实际数据所有权：

| 字段 | 含义 |
|---|---|
| `schema_version` | 当前为 1 |
| `group_key_version` | 当前分组算法 `spatial-footprint-road-policy-v1` |
| `policy_fingerprint_version` | 完整有序策略输入 hash 版本 |
| `road_fingerprint_version` | 与 ID、顺序、方向无关的规范道路 hash 版本 |
| `counts` | `training/validation/test/quarantined_training` 成员数 |
| `training[]`, `validation[]`, `test[]` | 三个实际 split |
| `quarantined_training[]` | 因与 final test 同组而移出的训练候选 |
| `diagnostic_reuse` | 指定 `--tile-ids` 时为 true，三份 split 有意复用 |
| `split_seed` | 分组留出随机种子 |
| `requested_validation_topologies` | 请求的 validation 成员数；原子分组会取最接近可达值 |
| `data_root`, `test_data_root` | 两个输入根的绝对路径 |

四个数组的每一行都有 `tile_id`、`group_key`、`policy_fingerprint` 和
`road_fingerprint`。`group_key` 优先用投影 CRS + footprint；元数据不足时退化到规范
道路 hash，再退化到策略输入 hash。`policy_fingerprint` 对 `features/entity_types/`
`edge_index/signal_entities/signal_action_mask` 的形状、dtype 和字节计算 SHA-256。

### 11.2 配置与初始化

- `resolved_config.json`：CLI 覆盖、旧字段迁移和 `land_use_order` 推断后的完整
  `TrainConfig`；未知配置键会报错。
- `initialization.json`：仅含 PPO 的四个来源字段。`type` 是从 checkpoint metrics 推断的 `sft/ppo/random_init/unknown_checkpoint`，无 checkpoint 时为 `random`；`checkpoint_path` 是绝对路径或 null；`checkpoint_sha256` 是文件 SHA-256 或 null；`cli_option` 是 `--init-checkpoint` 或弃用别名 `--sft-checkpoint`。纯 SFT run 不生成此文件。
- `train.log`：UTF-8 进程日志。复用输出目录会追加该文件，因此正式实验应使用新目录。

### 11.3 checkpoint

`random_init.pt`、`sft_best.pt`、`sft_last.pt`、`ppo_best.pt`、`ppo_last.pt` 都是
PyTorch dict：

| 键 | 含义 |
|---|---|
| `model` | 完整 `state_dict` |
| `optimizer` | AdamW state；`random_init.pt` 为 null |
| `step` | SFT epoch 或 PPO iteration；随机基线为 0 |
| `config` | 保存时的完整 resolved config |
| `metrics` | 该次保存对应指标；也用于推断初始化类型 |

写入先落到同目录 `.pt.tmp`，再原子替换目标。

### 11.4 本地指标镜像

- `wandb_history.jsonl`：每个 `RunLogger.log()` 事件一行。除指标外含单调 `_step`；
  显式 trainer step 时另含 `_trainer_step`。主要字段族为 `sft/train/*`、
  `sft/epoch/*`、`ppo/rollout/<task>/*`、`ppo/train/*`、`ppo/validation/*`、
  `evaluate/{validation,test}/<task>/*`，并分别用 optimizer/environment/iteration/
  checkpoint step 作横轴。PPO iteration 还记录 `ppo/rollout_steps_per_second`；启用
  Signal 时记录 `ppo/signal_rollout_workers`、`ppo/signal_rollout_seconds`、
  `ppo/signal_steps_per_second`。完整 checkpoint metrics 另含
  `ppo/rollout_seconds`。启动时 history 文件会被清空。
- `wandb_summary.json`：run summary 的本地 JSON 镜像，包括数据数量、模型参数量、
  SFT/PPO 最优值和 `train/ppo_initialization`、初始化 checkpoint 路径/hash、初始
  logit scale。每次 summary 更新均重写完整文件。

### 11.5 `evaluation_*.json`

自动训练评估会生成 `evaluation_validation_sft_epoch_NNN.json`、`evaluation_sft.json`
或 `evaluation_ppo.json`。顶层字段：

| 字段 | 含义 |
|---|---|
| `checkpoint` | 被评估 checkpoint 路径 |
| `deterministic` | greedy/ranked greedy 为 true，采样为 false |
| `rows[]` | 每个 task/tile 一行 |
| `summary` | 按 task 聚合的对象 |

每个 row：`tile_id/task/policy_reward/expert_reward/reward_delta/relative_gap_pct/episodes/`
`policy_metrics/expert_metrics/group_key`。其中
`relative_gap_pct=100*abs(policy-expert)/max(abs(expert),1e-8)`，越小越好。
`summary.<task>` 含 `policy_reward/expert_reward/reward_delta/relative_gap_pct/tiles/members`；
先在 `group_key` 内平均，再对组做 macro-average，`tiles` 实为组数，`members` 是原始
tile 数。

### 11.6 独立评估 ledger

`up-model-eval --output PATH` 原子写 `PATH`，并在旁边写
`PATH.with_suffix(".ledger.json")`。例如 `formal_test.json` 对应
`formal_test.ledger.json`。ledger 字段：

| 字段 | 含义 |
|---|---|
| `schema_version` | 当前为 1 |
| `created_at_utc` | UTC ISO-8601 时间 |
| `report_path` | 报告绝对路径 |
| `checkpoint_path`, `checkpoint_sha256` | checkpoint 绝对路径和所加载字节的 SHA-256 |
| `data_root` | 评估数据绝对路径 |
| `git_commit` | 可读取时为 40/64 位提交 hash，否则 null |
| `tasks`, `episodes`, `seed`, `deterministic` | 评估合同 |
| `tile_ids` | 过滤后的实际 tile 列表 |
| `requested_tile_ids` | CLI 请求列表；未过滤时为 null |
| `command` | shell-quoted 完整命令 |

`--fail-if-output-exists` 会同时保护 report 与 ledger。自动训练评估目前不写 ledger，
因此正式冻结的 final-test 报告应通过独立入口生成。

## 12. 模型加载后的张量格式

`load_urban_graph()` 将 abstract JSON 编译为：

| 张量 | 形状 | 含义 |
|---|---|---|
| `features` | `(N,32)` float | 静态特征 |
| `entity_types` | `(N,)` long | 0 parcel / 1 road / 2 junction |
| `edge_index` | `(2,E)` long | 每条无向关系存两个方向 |
| `parcel_entities`, `road_entities`, `intersection_entities` | 1-D | 全局索引 |
| `signal_entities` | `(J,)` | junction 全局索引 |
| `signal_action_mask` | `(J,8)` bool | 合法 canonical action |

实体顺序严格为 `[all parcels, all roads, kind=junction intersections]`。邻接边来自
parcel-neighbor/boundary-road/corner-junction、road-endpoint/adjacent-road/parcel；重复
关系去重。具体 32/18 维布局见[模型与训练](./模型与训练.md)。
